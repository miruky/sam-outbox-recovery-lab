# 設計と不変条件

## 注文の確定と配送の責任

注文、アウトボックス、受付件数の更新を1回のDynamoDBトランザクションへ含めます。注文だけ保存してイベントを失う二重書き込みを避け、EventBridgeへの配送は別の処理に担当させます。アウトボックスのキーは注文IDから導出する業務イベントIDであり、AWSが各配送へ付けるIDを重複判定には使いません。

StreamsのINSERTを受けた中継関数は、PutEventsの各エントリの成功を確認してからアウトボックスをSENTへ変更します。配送後、SENTへの更新前に停止した場合は同じイベントが再配送されます。集計更新と処理済みIDの保存を同じトランザクションに含めるため、配送の重複は二重加算になりません。

Streamsの保持期間は24時間です。中継が失敗した場合もアウトボックスを残し、`python scripts/lab.py recover-outbox --limit 100` で未送信データを再配送できます。Streamsの期限や中継用DLQのメタデータだけに復旧を依存させません。

## 再構築の成立条件

1. 制御レコードを条件付き更新し、新規注文を一時停止する。
2. 全アウトボックスがSENTであることを確認し、期待するイベントIDと金額の対応を固定する。
3. 最新の送信時刻から10分待ち、アーカイブから元のイベントバスへ再生する。
4. `Destination.FilterArns` を再構築用ルールだけに設定する。
5. 新世代でイベントIDごとに一度加算する。
6. IDと金額の対応、件数、合計の3条件を比較する。
7. 新世代をVERIFYINGにして新しい書き込みを拒否し、強い整合性のある読み取りで再比較する。
8. VERIFIEDであることを条件に、参照世代の変更、新世代のACTIVE化、旧世代のRETIRED化、ジョブの確定を同じトランザクションで行う。

件数と合計が同じでも、別のイベントへの置換や金額の入れ替えは正しい復元ではありません。期待するIDと金額の対応を比較して、相殺された不一致も検出します。照合中の書き込みを止める前後に再比較するため、比較直後に追加されたデータも見落としません。

旧世代を更新する通常処理は、制御レコードの世代が変わっていないこともトランザクションで確認します。切替と競合した更新はその条件で拒否されます。参照先切替後に届く重複は新世代の処理済みIDで除外されます。

再生のCOMPLETEDは配送側の完了です。下流の集計検証とは別に扱います。アーカイブのEventCountとSizeBytesは更新が遅れるため、完了判定に使用しません。再生順序も前提にせず、加算とイベントIDの重複排除だけに依存します。

## 通知の範囲

通知はDynamoDBへの模擬記録です。通知記録と処理済みIDを同じトランザクションで保存します。メールや外部APIを追加すると、外部送信とDynamoDBを同じトランザクションには含められません。その場合は外部サービス側の冪等キーや照合方式を別途設計する必要があります。

## 失敗時の振る舞い

- 処理用DLQは集計、通知、再構築で独立しています。
- EventBridgeの配送用DLQは、ターゲットへ渡せなかったイベントを保持します。関数内の処理失敗とは異なります。
- 中継用DLQとIteratorAgeアラームはStreams配送の失敗と遅れを検知します。
- 再構築で待機上限、不一致、API失敗に達した場合は旧世代を保持し、受付は停止状態に残します。
- 外側の状態機械全体がタイムアウトした場合や実行が手動停止された場合は、Catch経路が動かないことがあります。自動的な受付再開を前提にしません。
- リプレイの履歴はAWSが保持します。履歴表示の残存と稼働中のリソースを区別します。

## このサンプルから拡張するとき

アウトボックスを単一パーティションへ置き、照合時に最大1,000件の対応表を保持する構成です。高負荷の分散処理、DynamoDBの項目サイズ上限を超える対応表、多数の同時再構築にはそのまま適用できません。受付を止めない方式には、境界時点と差分取り込みを扱う別の設計が必要です。
